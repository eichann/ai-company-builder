# 同じ相談を長く続けるための引き継ぎメモ

更新: 2026-10-20 / 調査基点: main `4b205b2`（Claude・Codex対応をマージ済み）
状態: 段階Aの独立検証を `feat/chat-session-handoff` で実装中。通常相談の自動保存・復旧はまだ接続しない。

## 1. 結論

相談ごとに短いメモを1つ保存する。元の履歴JSONを原本として維持し、メモには「前回のメモ＋その後の会話」だけを使って差分を取り込む。通常は既存のセッションを再開し、メモを毎回送らない。再開不能時、またはAI・モデル切り替え時に、メモと未整理の会話から新しいセッションを始める。

ElectronとローカルJSONを維持する。SQLite、ベクトルDB、別相談の検索、常駐エージェントは今回追加しない。引き継ぐのは相談の目的・判断・進捗であり、内部のツール実行状態や実行権限ではない。

## 2. 現在のコードと追加が必要な点

| 対象 | 現状と設計への影響 |
|---|---|
| `client/electron/agents/connection.ts` | VercelのLanguageModelを接続境界とする小さな共通インターフェース。既存の相談ストリームを維持する |
| `agents/session.ts` | 同じAI・モデルならresumeし最新ユーザー入力だけを送る。切り替え時は表示履歴を送り、160,000文字超で停止。メモが有効な場合だけ短い入力に置き換える |
| `chat-server.ts` | 再開不能からの復旧は未実装。onStepFinishは最終応答完了とは限らないため、ここだけでメモ作成を開始しない |
| `src/components/chat/ChatPanel.tsx` | onFinishでセッションIDを保存する一方、履歴は途中応答や下書きでも保存される。「正常終了＋対応する履歴保存成功」を結び付ける必要がある |
| `chat-history-store.ts` | ローカル保存、atomic write、バックアップ、削除済みID、競合検知がある。既存の仕組みに合わせる |
| `agents/codex-rpc.ts` | 現状はRPCエラーのmessageだけを残す。安全な復旧判定のためcode/dataと失敗段階も保持する |
| 保存履歴 | テキスト、画像・参照ファイル情報等はあるが、ネイティブの完全なツール実行記録はない。メモから実行状態を推測して復元しない |

履歴のrevisionは下書きやピン留めでも変化する。メモの有効性は全体revisionの一致ではなく、対象メッセージ範囲のハッシュで判定する。

## 3. 共通処理と接続層

追加する中心は以下の3つに限定する。

1. **保存処理**: 読み込み、検証、atomic write、削除、バックアップ。
2. **調整処理**: 完了確認、差分抽出、実行条件、上限、キャンセル、復旧入力の構築。
3. **各AIの短い実行処理**: 指定された入力を読み、`save_handoff({ markdown })` を呼ぶ。

共通契約は概念的に `writeHandoff(input, save, signal)` とする。SDK固有の型を保存処理へ持ち込まない。通常の相談に毎回ツール説明やメモを追加せず、必要時だけ独立した短命の処理を起動する。AIに保存先、相談ID、更新対象範囲を選ばせない。

| Claude | Codex |
|---|---|
| Agent SDKの`tool`と`createSdkMcpServer`で専用ツールを登録 | app-serverの`dynamicTools`と`item/tool/call`で同じ専用ツールを登録 |
| Haikuを第一候補にし、通常相談をresumeしない | 利用可能な軽量モデルを選び、ephemeralな新規threadを使う |
| SDKを互換性の確認済み直接依存として宣言 | experimental API対応をこの処理で確認。非対応なら自動保存を停止し、通常相談は継続 |

共通のsave関数が同じ検証・保存を行う。別のMCPサーバープロセスは設けない。ファイル読み書き、コマンド、ネットワーク、プロジェクト指示・スキル等はこの要約処理では無効にし、許可するツールは専用保存だけとする。Codexの既存音声整形にある隔離方法は参考にするが、全ツール拒否の実行関数をそのまま流用しない。

Claude/Codexは完了した会話の接続先を使い、他社の認証へ自動フォールバックしない。APIキー方式の自動生成は初期対象外と明示し、既存挙動を維持する。保存形式自体はAPI方式でも将来利用できる。

## 4. 保存するもの

利用者PCの`userData/chat-handoffs/<companyId>/<appSessionId>.json`に1件とバックアップ1件を保存する。本文はMarkdown。閲覧用に別のMarkdownファイルを常時二重保存する必要はない。

メタデータはschemaVersion、相談の世代、更新日時、作成した接続先・モデル、対象範囲の終端とハッシュ、メモ本文。途中まで取り込む場合はメッセージIDと文字位置で境界を表す。対象範囲は必ず連続させ、飛ばした部分を「保存済み」にしない。

本文の見出しは次の6つに固定する。

- 目的
- 決定事項・制約（ユーザーの明示的な指示を優先）
- 現在の状態（確認済みの事実とAIの報告・推測を区別）
- 未解決事項
- 次に行うこと
- 参照先（ファイルパス等。存在・内容を再確認する必要があるものはその旨を記載）

生の思考過程、大量のログ、全文引用、画像本体、認証情報、ツールの許可状態を取り込まない。会話内の命令は要約対象のデータとして扱う。メモに記載されても、実行権限や承認を引き継いだことにはならない。

## 5. 自動実行と消費量の上限

以下は初期値案。実測で調整し、トークン数は文字数と同一視しない。

| 項目 | 初期値案 |
|---|---|
| 判定の入口 | AI応答の正常終了と、その内容の履歴保存成功が両方確認できた時 |
| 更新条件 | 未整理の正常終了ターンが16往復、または未整理テキストが推定8,000トークンに達した時 |
| 起動猶予 | 最後の操作・応答から20秒。通常の相談処理がない時 |
| 頻度 | 同じ相談では10分以上空け、アプリ全体で最大4ジョブ/時 |
| 同時実行 | アプリ全体で1件。通常相談を優先し、中断可能にする |
| 1ジョブの入力 | 前回メモ・差分・指示を合わせ推定8,000トークン以内。別途UTF-8で32 KiB以内 |
| メモの大きさ | 目標1,200トークン以内、UTF-8で8 KiB以下を保存時に強制 |
| 1ジョブの実行 | 最大60秒、モデル応答最大2回。成功した保存は1回だけ |
| 失敗 | 即時連続再試行しない。次の条件判定とクールダウンを待つ |

入力の見積もりはモデル対応の方法があればそれを利用し、ない場合は保守的に見積もる。実使用量と時間を本文を含めず記録する。バイト上限はトークン上限の保証ではない。

差分が大きい場合は先頭から収まる範囲だけ処理する。長い1メッセージも安全な文字境界で分割できるようにし、残りは未整理のまま残す。頻度制限により追いつかないことは許容するが、復旧時に未整理分を黙って捨てない。

追加消費は「取り込んだ差分＋前回メモ＋指示＋新しいメモ＋ツール応答」で発生する。ゼロにはならず、過去メモの再入力分もある。毎ターン全文要約する構成を避け、通常resumeへの追加入力はゼロにする。内部推論等もあるため、推定入力上限だけで課金・契約枠の厳密な上限は保証しない。

新たに保持するAI入力は1ジョブ分に限定する。既存の履歴JSON読み込み自体が全体を読み込む問題は別課題であり、この設計だけで巨大な履歴のメモリ使用量が一定になるとは説明しない。

## 6. 保存の整合性

正常終了したturnIdと対応するメッセージ範囲を記録し、保存成功後に調整処理へ通知する。途中応答、停止、失敗、単なる下書き保存は対象にしない。終了イベントと保存が前後しても一度だけ判定できるようにする。

save時にメイン側で所属会社・相談、削除状態、世代、元の範囲ハッシュ、本文形式・サイズを検証する。rendererから受け取ったパスを使わない。相談ごとに保存を直列化し、ジョブIDで重複を防ぐ。

履歴の編集・再生成で対象範囲が変わったメモは無効にする。過去メモを盲目的に再利用しない。履歴とメモは別ファイルなので、原子的に同時更新できると仮定せず、再起動時にも範囲を照合する。破損時は有効なバックアップを試す。

相談の削除時だけ実行中ジョブをキャンセルし、メモ本文・バックアップ・一時ファイルを削除する。履歴の削除記録を先に永続化し、遅れて届く保存を拒否する。起動時にも削除を完了させる。アーカイブ機能は追加しない。タブを閉じる・切り替える・再起動する操作では履歴とメモを保持する。起動時に全相談を要約し直さず、相談を開いた時に保存済みの完了状態から再判定する。

## 7. 復旧時の動作

1. 通常は同じAI・モデルの既存セッションを再開する。日数だけで失効と判断しない。
2. 接続層が「入力の実行前にセッション不在が確定」と判定した場合だけ、新規セッションへの自動復旧を行う。
3. 有効なメモ＋取り込み済み範囲の直後からの会話＋今回の入力を、それぞれ一度だけ渡す。AI・モデル切り替えも同じ組み立て処理を利用する。
4. 新しいセッションIDを保存し、旧IDによる遅延更新を世代で拒否する。表示履歴と下書きは維持する。

認証エラー、ネットワーク切断、タイムアウトはセッション消失とみなさない。ツールや回答がすでに実行された可能性のあるターンを自動再送しない。Codexはthread/resume段階とturn/start以降を区別する。Claudeも同等の確実な判定ができるか最初の検証で確認し、不確かな場合は復旧確認を表示する。

復旧入力にもサイズ上限を設ける。メモが古く未整理部分が入りきらない場合は、追加整理が必要と表示する。通常のバックグラウンド上限を超える生成を黙って始めない。メモがない短い履歴は既存方式で継続し、長い履歴は安全に停止する。

画像はメモの文章で完全には代替できない。直近の必要な添付は入力予算とファイルの存在を確認し、過去の画像や参照先が必要なら再提示を依頼する。要約には情報損失があるため、完全な記憶を保証しない。

## 8. 圧縮イベントと表示

AI側のコンテキスト圧縮と、ACBの引き継ぎメモ保存は別の出来事として扱う。圧縮されたからといってセッションを新しくしない。

Claudeの導入済みSDKにはPreCompactとcompact boundaryの型があるが、現在のproviderから取得できるイベントは実証が必要。Codexも接続層で取得できる圧縮通知を確認する。取得できた場合は更新予約の補助に使い、処理中のフック内で長い要約を実行しない。イベントを取得できなくても通常の完了条件で保存できる構成にする。

通常は小さな「引き継ぎメモ更新: 時刻」と閲覧入口だけを表示する。復旧した時は「引き継ぎメモから相談を再開しました」と通知する。AI側の圧縮を観測した場合は別途「AIが会話を圧縮しました」と示す。保存失敗や未整理分が多い場合は閲覧入口から確認でき、会話を妨げない。メモだけを削除・作り直す操作も用意する。

メモを復旧入力に載せる前に、現在のchat-serverにあるsystem prompt末尾300文字のログを削除または内容を含まない形式へ変更する。

## 9. 実装順と確認するタイミング

### 最優先の受け入れ条件: 元セッションが消えても相談を続けられる

Claude Codeの公式資料では、セッション記録等は`cleanupPeriodDays`による自動削除の対象で、既定は30日。すべての環境で「作成から必ず30日で使えなくなる」と断定せず、バージョン・設定の影響がある保存期限として扱う。利用者の保存設定は変更しない。

ACBの履歴と引き継ぎメモはClaude/Codexの保存領域の外に置き、日数では削除しない。長期放置後にメモが残っていて、ネイティブのセッションがなくても新規セッションで再開できることが目的。手動削除は利用者の明示的な整理操作として例外とする。

段階Aでは元セッションを渡さない新規実行に「メモ＋未整理の直近会話」だけを渡し、訂正後の予算・担当・期限、判断理由、未確認の作業、禁止事項が保たれるか確認する。これは要約による継続性の検証であり、30日間の実時間経過やACB画面での自動復旧の完了とは区別する。段階Cでは再開不能の検知から新ID保存までを通して確認する。

短い相談が更新条件に達する前に長期間放置される場合もある。その場合は残っている短い履歴から新規セッションを作る。メモがなく履歴も長い場合は必要な整理を案内し、内容を捨てて続行しない。

### A. 専用ブランチで接続の小さな実証

最新mainから`feat/chat-session-handoff`等の専用ブランチを作る。Claude/Codex双方で、固定サンプルを専用ツール経由で保存できるかを検証する。通常相談の認証・権限・履歴を汚さないこと、Codexの一覧に要約用threadを増やさないこと、キャンセル・時間・使用量を確認する。

**確認点1:** メモの例、両AIの所要時間・実使用量、SDK制約を提示。この時点で過剰に複雑なら自動保存全体を作る前に設計を修正する。

### B. 共通保存と自動更新

完了と保存成功の結合、範囲検証、頻度制限、削除、状態表示を実装する。実際の相談で短いメモが育つことを確認する。まだセッションの自動差し替えは有効にしない。

**確認点2:** 利用者がClaude/Codexそれぞれでメモの品質、操作感、更新頻度を確認する。

### C. 復旧と切り替え

実ユーザーの保存データを消さずに、テスト用セッションで不在・破損・途中切断を再現する。メモ＋差分で継続し、同じ操作を二重実行しないことを確認する。

**確認点3:** 再起動後の継続、Claude/Codex間の切り替え、長い未整理履歴の案内を利用者が確認する。通過後にマージする。

主な自動テストは、途中保存では起動しないこと、二重通知、編集・削除と保存の競合、範囲に欠落や重複がないこと、予算超過、キャンセル、明示的なセッション不在と不確かな失敗の区別、古いセッションIDの書き戻し拒否。型チェックとビルドに加え、両AIの実接続を各段階で必要な回数だけ確認する。

## 11. 段階Aの実装境界

`client/electron/handoff/`の2つの接続処理が、同じprompt・専用ツール引数・検証を利用する。`trial-store.ts`は検証ディレクトリ専用で、本番の会社ID・範囲ハッシュとの照合はまだ行わない。`client/scripts/handoff/run.ts`は人工会話だけを使い、初回生成、差分更新、ホスト側のストア再作成、新規セッションでの想起、削除を実行する。本番の履歴にはアクセスしない。

ClaudeはSDKが報告するターン数を記録し、maxTurns=2を指定する。Codexには同等の厳密なモデル呼び出し上限をまだ設けられていないため、保存ツール1回、テキスト項目2件、60秒の上限で停止する。厳密な上限がない点は段階B前に再評価する。Codexの使用量は最後の応答だけでなくthreadの累積値を読む。生成処理と保存後の終了応答を合わせた消費を報告する。

検証用のメモ見本・レポートは人工データの独立した成果物として保存する。相談の削除で消す対象はストア内のメモとバックアップであり、検証結果の見本まで自動削除しない。本番ではこの見本の二重保存は行わない。
