# 同じ相談を長く続けるための引き継ぎ設計案

## 2026-10-20 更新：引き継ぎより先に接続層を分離

今回の実装範囲は相談の接続層のみ。引き継ぎ生成・保存・自動実行・復旧とCodex接続は未実装。以下の引き継ぎ案より、この節の責務分担を優先する。

### 小さな共通契約

`client/electron/agents/connection.ts` の `AgentConnection` は、認証状態、相談用／タイトル用モデルの生成、会話を接続先が保持するか、実行結果のセッションID・使用量の正規化だけを扱う。Vercel AI SDKのLanguageModelを既存のストリーム処理との接続口として使う。独自のエージェントループ、イベントバス、プラグイン登録機構は追加しない。

- `agents/claude.ts`：Claude Codeモデル名・effort変換、CLI起動（Windows対応とElectronのFD対策）、resume、PreToolUse、canUseTool、Claudeメタデータの解析。相談とタイトルで起動処理を共有。
- `agents/anthropic-api.ts`：従来のAPIキー方式とreasoning middleware。会話履歴はACBが送る。
- `chat-server.ts`：HTTP、Vercelストリーム、入力・画像、履歴の送信範囲、画面への承認依頼、正規化された使用量の保持を担当。起動設定で接続先を選ぶ。

内部の再開IDはproviderIdと組にして保持し、異なる接続先へ渡さない。既存の履歴JSONとHTTPの `claudeSessionId` は互換性のため維持する。これはClaude用の移行境界であり、汎用の永続形式ではない。Codex対応時にはproviderIdとsessionIdの組を永続形式にも追加し、旧フィールドをClaudeのIDとして読む。今回、既存履歴の移行や再開失敗時の再試行は行わない。

### Codex対応への境界と残る作業

Codexのモデル名を差し替えるだけでは対応しない。新しい接続実装が、実行・中止・承認・再開・使用量を既存のモデル／ストリーム契約へ変換する必要がある。現行のモデル選択画面と認証設定も、その時点で拡張する。既存のClaude固有設定はClaude接続の型に閉じ込め、共通契約には持ち込まない。

音声整形の `claude -p` は独立した経路のため今回対象外。すべてのAI経路の抽象化が完了した、という意味ではない。

### 後続の引き継ぎ実装

保存形式、保存先、検証、サイズ上限、重複防止、スケジューリングはACB側に置く。Claude Agent SDKのカスタムツール登録と短時間の要約実行はClaude接続側に置く。保存処理本体はSDK型に依存させず、カスタムツールから共通の保存関数を呼ぶ。

引き継ぎを着手するときに必要最小限の実行メソッドを契約へ追加する。未使用のメソッドや仮のCodex実装は今は作らない。自動圧縮通知や再開不能判定も、生のClaudeイベントを画面へ漏らさず接続層で正規化する。元の設計のトークン・入力サイズ・実行頻度上限は維持する。

今回の分離そのものでは追加のAI呼び出しや履歴複製を行わない。メモリとトークン消費の増加を伴う常駐処理も追加しない。

### 確認

接続層のテストでresume／effort、タイトル生成との分離、危険操作の承認、バックグラウンド子エージェントの抑止、読み取り操作の許可、メタデータの正規化を確認する。型チェックと配布用ビルドを実行する。実際のClaude認証・会話再開・承認ダイアログについては、開発版で利用者が確認する。

## 1. 推奨する最小構成

**既存の履歴を原本として残し、相談ごとに短い引き継ぎメモを1つ持つ。更新は差分だけ、利用はClaudeのセッションを復旧するときだけ。**

Electron、既存の履歴JSON、現在の相談用プロバイダーは維持する。SQLite、ベクトルDB、常駐エージェント、全文の別コピーは追加しない。

メモの更新には、Agent SDKで起動する短命なHaiku処理を使う。「前回のメモ＋未整理の会話」を読み、専用の `save_handoff` カスタムツールで保存する。実行するタイミング・入力の範囲・保存先はACBが決め、AIには内容の整理だけを担当させる。

通常の相談はこれまでどおりClaudeのresumeを使い、メモを毎回注入しない。セッションが失われた場合だけ、メモと未整理の会話を渡して新しいClaudeセッションに接続し直す。ACB上の相談ID・履歴・下書きは同じものを維持する。

「1か月で必ず切れる」という日数判定は実装しない。CLIの保存状態・設定などに依存するため、実際の再開結果を判定する。

## 3. 保存するもの

保存先（利用者ごとのローカルPC）:

`userData/chat-handoffs/<companyId>/<appSessionId>.json`

1相談につき現行1ファイル＋直前の正常なバックアップ1ファイルだけ。JSONにMarkdown本文を格納し、本文と管理情報を1回のatomic writeで更新する。Markdownを別ファイルへ二重保存しない。必要なら表示・エクスポート時に.mdを生成する。

### AIが書く本文

見出しは次の6つに固定する。空欄は「なし」とし、推測で埋めない。

1. **目的**: この相談で達成したいこと。
2. **決定・制約**: 確定した方針、理由、ユーザーの明示的な希望・禁止事項。
3. **現在地**: 完了したこと、実行中のこと、確認済み／未確認の区別。
4. **未解決事項**: 保留、障害、確認が必要なこと。
5. **次の一手**: 再開後に着手すべきこと。
6. **参照先**: 関係するファイル・PR・URLなど。存在確認済みかどうかも区別する。

発話全文、思考過程、巨大なツール出力、画像、毎回の挨拶、トークン・APIキーなどの秘密値はメモへ複製しない。ツールによる作業の詳細がACBの履歴に残っていない場合、推測で「実行済み」にせず再確認事項にする。

前のメモを更新する際は、まだ有効な決定を保持し、明示的に変更された事項だけ置き換える。「新しい部分だけの要約」にして過去の決定を消さない。

### ACBが付ける管理情報

- schemaVersion / companyId / appSessionId
- checkpointRevision / updatedAt
- 対象履歴の世代、整理済み位置（messageId、必要な場合だけ本文内のoffset）
- 対象範囲を識別するfingerprint
- 更新理由、利用モデル、実測usage、最終エラーの種類

保存先や整理済み位置をAIに指定させない。実行開始時にACBが固定する。新しい発話が末尾へ追加されても古い範囲のメモは保存できるが、対象範囲が編集・再生成された場合は古い結果を破棄する。

## 4. カスタムツールは1つ

`mcp__acb_handoff__save_handoff({ markdown })`

`tool()` と `createSdkMcpServer()` でElectron内に登録する。別のMCPサーバープロセスは立てない。引数は固定見出しを持つMarkdown本文だけ。メモは追記ではなく全体置換する。

ハンドラー側で:

1. サイズと必須見出しを検証する。
2. 実行時に固定した相談ID・対象範囲・checkpointRevisionを照合する。
3. 相談が削除されていないこと、対象履歴が変更されていないことを確認する。
4. メモをatomic writeし、「保存済み」の短い結果だけ返す。

有効な保存は1ジョブにつき1回。検証エラー時だけ1回の修正機会を認め、無限に再試行しない。保存ツールが成功した後にSDKの終了処理が失敗しても、既に正常保存したメモは巻き戻さない。

専用処理の基本設定:

- model: haiku、resumeなし、persistSession: false
- built-in tools: 空、利用可能なMCPはこのツールだけ、strict MCP設定
- user/project設定・CLAUDE.md・スキル・自動メモリーを読み込ませない隔離用cwdと設定
- 通常相談の高いeffort設定を継承しない
- maxTurns: 3、45秒タイムアウト、AbortController
- `canUseTool`等の制御はこの1ツールだけ許可する。通常相談の権限制御を弱めない
- 結果ストリームは処理後破棄し、相談履歴へ内部会話を追加しない

これらは既存SDK 0.2.47のAPIとインストール済みCLIの組合せで小さな接続検証をしてから確定する。SDK更新が必要なら、この機能とは切り離して互換性を確認する。既存のmacOS EBADF対策、Windows用起動処理も共通化して再利用する。

## 5. いつ自動実行するか

初期値は次のとおり。設定画面を増やさず、最初は内部定数で運用する。

| 条件 | 動作 |
|---|---|
| 未整理の完了ターンが8往復以上 | 次の応答完了・履歴保存成功後に更新候補にする |
| 未整理のユーザー／アシスタント本文が合計12,000文字以上 | 8往復未満でも更新候補にする |
| PreCompact通知 | 更新必要フラグと小さなUI通知だけを付ける。フック内でLLMを呼ばず、応答完了後の更新候補にする |
| CLIセッションが失われ、メモだけでは再開できない | 下記の復旧処理で必要な差分を整理する |
| 起動、タブ切替、下書き入力、1秒ごとの履歴保存 | AIを呼ばない |
| アプリ終了 | AI処理を待たずに終了する。保存済み履歴とメモから次回再開する |

更新候補になっても、通常相談が動いている間は実行しない。応答完了から5秒ほど操作がなければ開始する。自動実行はアプリ全体で同時に1つ、開始間隔は最低5分。待ち行列には相談IDだけを入れ、本文を複製しない。

新しい相談応答が始まったら、未着手の更新を延期し、実行中の更新はキャンセルする。これで会話の操作感を優先する。キャンセル・失敗時は整理済み位置を進めず、次の機会へ持ち越す。

短い相談は要約しない。CLIセッションがなくなっても、短い履歴ならそのまま復旧入力に収まるため。

## 6. メモリ・トークンの上限

### 1回の更新

- メモ本文: 目安800〜1,500トークン。保存時はUTF-8で8KiBを上限にする。
- 新規会話差分: UTF-8で24KiBまで。前回メモと指示を含め、可変テキスト全体を最大36KiBに制限する。
- 長文はメッセージ境界、必要なら本文の段落境界で分割し、整理済み位置を進める。途中を黙って捨てたり、読んでいない範囲を整理済みにしない。
- 1回の起動では1チャンクだけ。残りがある場合も連続起動せず、次の実行機会へ持ち越す。
- 出力上限・maxBudgetUsdはSDK/CLI互換性を確認して適用する。初期の予算上限案は1ジョブ0.05米ドル相当。実usageとキャンセル数を記録し、実測で調整する。

**文字数・バイト数をトークン数と同一視しない。** 通常の目標は入力数千〜1万程度・出力2千トークン以内だが、日本語の内容やツール定義、SDK内部プロンプトでも変わる。バイト上限は入力とメモリの制限、API usageは課金量の観測として分ける。金額の予算値も請求額の完全な保証として表示しない。

毎回要約する方式と異なり、更新のないターンは追加の要約リクエストが0回。専用処理は通常相談の長いコンテキストをresumeしないため、蓄積した全会話を繰り返し入力する費用を避けられる。ツール呼び出し後の最終応答でも追加モデル呼び出しがあり得るので「ツール1回だからAPIも1回」とは数えない。

### メモリ上の注意

追加のデータは1ジョブの短い入力・メモとIDの待ち行列だけ。ただしClaude CLI自体のプロセスメモリは別に必要であり、軽量な常駐処理だとは言わない。1プロセスずつ使い、終了時に解放する。

既存の会社別JSONは全件読み込みで、rendererも開いている相談を保持する。今回の設計は**追加する要約処理の消費を制限する**もので、既存アプリ全体のメモリを一定量にするものではない。履歴一覧の「続きを読み込む」も現状は表示の分割であり、ディスク読み込みの分割ではない。

## 7. セッションが失われたときの復旧

1. 通常は保存済みのClaudeセッションIDでresumeする。
2. 「指定セッションがない／再開できる保存データがない」と判別できるエラーだけを復旧対象にする。認証、通信、利用上限、権限、ユーザーキャンセルでは再実行しない。
3. 応答やツール実行が始まる前のエラーに限り、1回だけ新規セッションへ切り替える。実行途中のエラーを自動再送して副作用を二重実行しない。
4. 新規入力は「現在のシステム指示＋メモ＋整理済み位置以降の会話＋今回の発話」。今回の発話は1回だけ含める。メモを上位指示として扱わず、過去の相談の要約であることを明示する。
5. 未整理部分が入力上限内ならそのまま渡す。長すぎる場合は、最大2チャンクまで差分整理してから復旧を再判定する。それでも収まらなければ黙って中間の会話を切り捨てず、「引き継ぎの整理が必要です」と表示し、利用者が続行できるようにする。特に導入前の巨大な履歴はこの例外になり得る。
6. 新しいCLIセッションIDはmain側の履歴ストアで保存し、rendererへ反映する。ACBの相談IDは変えない。

一度の送信につき新規セッションへの切替は最大1回。接続障害を復旧と誤判定してループしない。SDK/providerのエラー形状は現行バージョンで実測し、判別できないエラーを推測で分類しない。

### セッションIDの所有権を明確にする

復旧後のIDはmain側を正とする。rendererから届く古いclaudeSessionIdは上書きに使わない。ChatHistoryStoreに専用の更新・解除操作を用意し、古い下書き保存がセッションIDを復活させないようにする。既存履歴のIDは初回読み込みで引き継ぐ。

HTTPリクエストにはcompanyIdを追加し、appSessionIdだけでなく会社と相談の組を検証する。メモの保存・参照はその組に固定し、AIに他の相談IDや任意の保存パスを渡させない。

## 8. UIへの出し方

- 更新中だけ「引き継ぎメモを更新中」、完了時は控えめな短い通知。
- セッション復旧時は「保存した文脈から相談を再開しました」。必要なら最終メモ更新日時を表示する。
- 失敗時は「履歴は保存済みです。引き継ぎメモの更新は後で再試行します」。通常の相談は止めない。
- PreCompact検出時は「会話の文脈を自動整理しています」。検出だけで完了と表示しない。
- メモの閲覧は小さな詳細表示から。通常の会話に内部メモやツール実行を大量表示しない。

初版ではPostCompact完了イベントや、providerの内部ストリーム横取りを追加しない。compact_boundaryを正確に扱う必要が出た段階で、provider更新または正式なイベント転送口を検討する。Queryのiteratorを2か所から読む実装は避ける。

## 9. 故障・編集・削除時のルール

- 原本は既存履歴。メモの更新失敗で履歴を変更・削除しない。
- 履歴の過去メッセージ編集・再生成がメモの対象範囲に及んだら、そのメモを無効化する。新しい末尾の追加や下書き変更では無効化しない。
- 同じ相談の更新ジョブは重複起動せず、対象範囲とcheckpointRevisionで遅延書き込みを拒否する。
- 相談削除時は先に既存の削除済みIDを確定し、ジョブをキャンセルし、メモとバックアップも削除する。遅れて届く保存は拒否する。削除後のメモ孤立ファイルは起動時の軽量な清掃対象にする。
- 正常なメモだけを置き換える。読み取り破損はバックアップへフォールバックし、どちらも壊れていればメモなしとして扱う。
- 長期間使っていないという理由だけではメモも履歴も消さない。

## 10. 変更範囲と実装順

新しい本体ファイルは概ね3つで足りる。

1. `chat-handoff-store.ts`: スキーマ、サイズ検証、atomic保存、バックアップ、対象範囲チェック。
2. `chat-handoff.ts`: 差分の切り出し、実行条件、1本のジョブ管理、SDKツール定義。
3. `shared/chat-handoff.ts`: 必要最小限の型と状態通知。

既存の `chat-server.ts`、`main.ts`、`ChatHistoryStore`、`ChatPanel.tsx` に接続する。段階ごとに利用者が確認できるようにする。

### A. 小さな接続検証

インストール済みSDK/CLIで、隔離したHaikuからカスタムツールを1回呼んで保存できること、上限・キャンセル、macOS/Windowsの起動経路を確認する。通常相談の置換はしない。

**確認地点:** 保存されるメモの実例と、1回あたりの入力・出力トークン、所要時間を見てもらう。

### B. 自動保存

応答完了と履歴保存の成功を結び付け、差分更新・閾値・削除連動を実装する。まずメモ品質と費用を確認する。内部の保存成功を待たず「保存できた」と表示しない。

**確認地点:** 数回の相談で、確定事項・未解決事項が適切に残り、応答が遅くならないか確認する。

### C. 同じ相談での復旧

セッション不在をテスト環境で再現し、メモ＋差分から新規CLIセッションへ切り替える。現在の利用者の実セッションファイルを削除するテストはしない。

**確認地点:** 同じ相談画面のまま方針を引き継げること、履歴・下書き・メッセージが重複しないことを確認する。

主な自動検証: 差分境界、長文分割、閾値、失敗時cursor不変、編集による無効化、削除後保存拒否、古いrendererによるID巻戻し防止、認証/通信エラーで再送しない、ツール実行後に二重実行しない、キャンセルとプロセス解放。

## 11. 採用しない方式と理由

| 方式 | 今回採用しない理由 |
|---|---|
| 毎ターン、全文を別モデルで要約 | 会話が長くなるほど入力トークンが増える |
| Stopフックで本体に毎回メモを書かせる | 長い本体コンテキストを追加で処理する可能性があり、応答完了も遅くなる |
| PreCompactの中から別のresumeを起動 | 同じセッションの並行更新・待ち・再入が複雑になる |
| 常駐したメモリー専用エージェント | 常駐メモリとライフサイクル管理が増える |
| Claudeのjsonlを丸ごと別保存 | ACB履歴と二重管理になり、引き継ぎに必要な文脈の整理にもならない |
| ベクトル検索、他相談への自動アクセス | 今回の「同じ相談の継続」には不要。別段階で設計する |
