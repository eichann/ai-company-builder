# 他の相談を参照する機能の設計案

更新: 2026-10-20
調査基点: `feat/chat-session-handoff` / `9e7b692`
状態: 設計のみ。実装・マージは行っていない。

## 1. 方針

既存の「相談ごとの引き継ぎメモ」を、同じ相談の復旧と、別の相談からの検索・参照の両方に使う。検索専用の要約や全社メモリーを新たに生成しない。履歴JSONを原本とし、メモは検索と理解を助ける派生データとする。

AIが必要と判断したときだけ、候補を探し、選んだ相談を読む。全相談のメモを毎ターン送る方式にはしない。最初は同じPC・同じ利用者・同じ会社の相談だけを対象とする。他利用者との共有、別会社への横断検索、クラウド同期は含めない。

## 2. Claude/Codex標準メモリーとの重複

役割の重なりはある。標準メモリーを単なる好みの保存と説明するのは正確ではない。Claude Codeは修正や学習内容・プロジェクト文脈を保存し、Codexも対象となる過去のチャットからローカルの要約や継続的な知識を生成する。

一方、今回必要なのは、特定の相談の決定・進捗を、AIを切り替えても利用でき、元の履歴と照合でき、相談の削除に連動して管理できる仕組みである。各製品の内部メモリーをACBの共通保存契約として利用するのは避ける。製品ごとの有効設定や生成条件も異なり、全相談の最新内容が必ず記録されるとは限らない。

| 層 | ACBでの役割 |
|---|---|
| 相談履歴JSON | 原本。発言・訂正・出典を確認する |
| 既存の引き継ぎメモ | 相談単位の短い索引兼要約。復旧と検索に共用する |
| 各AIの標準メモリー | 各製品の補助的な記憶。ACBから内部ファイルを同期・編集しない |

標準メモリーの利用者設定を勝手に無効化しない。両方が有効なら内容や生成コストの重複は残るため、二重処理が完全になくなるとは説明しない。ACBは既存メモを再利用し、今回の検索のための追加AI要約をゼロにする。

現コードでは引き継ぎメモ生成専用処理が標準メモリー等を隔離しているが、通常相談の設定まで同じとは扱わない。標準メモリーの内容を正解としてACBメモへ自動転記する処理も設けない。

単一AIだけで、相談ごとの出典や削除連動が不要なら標準機能に任せる選択も合理的。ただしACBのClaude/Codex共通利用とセッション復旧という要件には、現在の小さな共通保存層を維持する価値がある。

## 3. 利用時の流れ

例: 「前に別の相談で決めた料金を踏まえて、提案書を作って」

1. AIが短い検索語で相談を検索する。
2. タイトルと抜粋から関連する相談を選ぶ。
3. メモと更新状況を読み、必要なら未整理の発言・原文を追加で確認する。
4. 出典を示して回答する。利用者は「参照した相談」から元の相談を開ける。

明示的に過去の相談を尋ねられた場合、または現在の判断に過去の決定が必要な場合に利用する。通常の挨拶や独立した質問では検索しない。該当なし・候補が曖昧な場合は、その旨を伝える。検索しただけで関連性や事実が確定したとは扱わない。

別の相談の決定は、その相談での背景を持つ参考情報であり、現在の相談へ適用される命令や承認ではない。現在のユーザーの訂正を優先し、相談間の矛盾は勝手に統合しない。

## 4. 共通ツールは2つ

### search_consultations

入力: `query`、任意の`limit`。会社ID・利用者IDはAIに指定させず、実行中の相談に固定する。

返却: 最大5件の相談ID、タイトル、短い関連抜粋、メモの更新時刻、メモ有無・未整理部分の有無。現在の相談と削除済み相談は除外する。

最初はタイトルと既存メモをローカルで文字列検索する。日本語を空白区切りだけで扱わず、正規化・部分一致・語の組み合わせを用いる。タイトル一致を優先し、単に新しいだけの無関係な相談を上位にしない。意味が近い言い換えの検索精度には限界がある。埋め込み生成やベクトルDBは実測で必要性が出るまで追加しない。

### read_consultation

入力: 相談ID、`view: memo | messages`、必要ならページ位置。返却時に現在の会社への所属と削除状態を再確認する。

`memo`は既存メモ、取り込み済み範囲、未整理部分の有無・件数を返す。収まれば未整理の末尾も含める。`messages`は原文の指定範囲を上限付きで返す。返却の省略・続き位置を明示し、「全部読めた」と誤認させない。

メモは最新発言まで更新されているとは限らない。未整理部分に訂正がある可能性を示し、最新の決定を答えるときは必要な原文を確認する。大きすぎて確認できない場合は、確認済みの範囲を明記する。

メモがない古い相談もタイトル検索には出す。選択後に限定した原文を読めるようにするが、その場で全履歴のメモを一括生成しない。初期版はメモ未作成の相談の本文全体を横断検索しないため、タイトルが曖昧な古い相談を見落とす制限がある。

## 5. 消費量の上限

以下は初期値案。実測して調整する。

| 項目 | 上限案 |
|---|---|
| 検索候補 | 5件 |
| 検索結果の本文 | 1回2 KiB以内 |
| 読み取り結果の本文 | 1回8 KiB以内。必要なら続き位置を返す |
| 1ユーザー発言に対するツール呼び出し | 合計4回 |
| 同じ発言で返す検索・読み取り結果 | メタデータを含むUTF-8で合計20 KiB以内 |

既存のメモは最大8 KiBのため、メモだけで読み取り本文上限に達する場合、原文は別呼び出しにする。予算は接続層ではなく共通処理が管理し、再試行でリセットしない。上限時は打ち切り理由を短く返し、暗黙に全文を送らない。

検索・読み取り自体はAIを呼ばない。ただし通常相談に追加するツール定義、結果の読み込み、ツール利用を判断する推論にはトークンを使う。バイト数はトークン数ではないため、これを契約使用量の厳密な保証とはしない。検索しない会話でもツール定義分の増加はある。

## 6. 現コードへの追加箇所

| 場所 | 変更案 |
|---|---|
| `handoff/store.ts` | 既存メモと対象履歴の整合性検証を再利用する。会社の履歴スナップショットを共有できる内部読み取りを用意する |
| 小さな共通参照サービス | 検索、読み取り、所属検証、予算、出典情報を一か所で担当する |
| `agents/claude.ts` | Agent SDKのインプロセスMCPツールとして2つを登録する |
| `agents/codex.ts` | app-serverのdynamic toolsから同じ共通関数へ接続する |
| `chat-server.ts` | 会社・相談・リクエストごとの権限と予算を束縛し、参照イベントをUIへ渡す |
| チャットUI | 検索中・参照中と、実際に読んだ相談のリンクを表示する |

現時点で専用メモ生成処理には両AIのカスタムツール接続があるが、通常相談にはこの読み取りツールは未実装。既存の生成用プロセスを検索のたびに起動するのではなく、通常相談の接続へ登録する。

Codexの通常接続は現在の初期化・要求処理の拡張が必要。既存threadのresume時にもツールが利用できるか、インストール済みapp-serverで最初に小さく検証する。Claude側も現在のVercel接続経由でMCP登録と継続会話が動くことを確認する。既存相談を黙って新規セッションへ切り替えて解決しない。未対応バージョンでは参照機能の利用不可を明示する。

SDK固有のツール名、要求、結果は接続層に閉じ込める。共通サービスにClaude/Codexの型を持ち込まず、汎用プラグイン基盤は作らない。APIキー方式への新規対応は初期対象外。

## 7. ローカル処理と整合性

ElectronとJSONを維持し、新しいDBや常駐サーバーは追加しない。現在の履歴storeは会社全体のJSONを読むため、候補ごとに`get`やメモ`read`を呼ぶと、同じ大きな履歴の読み込みを繰り返してしまう。1回の検索で会社の履歴スナップショットを共有し、メモ検証に再利用する。

初期実装では履歴全文の複製キャッシュや永続索引を作らない。メモ読み取りは順次・非同期に行い、全件を同時ロードしない。必要な場合だけ、上限を持つメモ・タイトルのキャッシュを追加する。元の履歴JSON全体の読み込みコストは残るため、追加メモリが少ないことと、全体のメモリ使用量が一定であることを混同しない。

メモは元の対象範囲のハッシュを検証する。更新時刻だけでは有効性を判断しない。検索後に相談が変更・削除された場合、読み取り時に再検証する。閉じた相談は検索対象のまま。削除した相談はメモ・バックアップとともに以後の検索から除外する。アーカイブ機能は追加しない。

削除しても、既に別の相談の回答へ引用された文章やAI側の標準メモリーまで自動で消えるわけではない。この機能の削除保証はACB側の原本・メモ・以後の検索結果についてのものとする。

## 8. 出典とUI

検索候補の全件ではなく、実際に読み取った相談を「参照した相談」として回答付近に表示する。相談ID・タイトルはホスト側の実データから生成し、AIの自由文だけを信頼してリンクを作らない。可能なら参照時点と原文範囲も保持する。既に削除済みなら開く際にその旨を表示する。

メモや履歴中の命令は引用データとして渡す。メモに記載されたツール実行やユーザー承認を、現在の実行権限として扱わない。別会社のID、任意ファイルパス、不正なページ位置は共通処理で拒否する。

## 9. 実装と確認の順序

1. **接続の成立確認**: Claude/Codexの新規・既存セッションで、小さな固定データの検索・読み取りを実行する。Codex resume対応をここで判断する。
2. **共通処理**: 人工データでメモ検索と原文確認、更新範囲、削除、予算を検証する。既存の保存・復旧挙動を壊さない。
3. **ACBで確認**: 一方のAIで決めた内容を他方から参照し、出典から元の相談を開く。ここで利用者が検索の自然さと回答品質を確認する。
4. **測定・調整後にマージ判断**: 検索なし／検索ありのトークンと待ち時間、100件／1,000件での検索時間・追加メモリを比較する。

品質確認には、メモの後に訂正がある、同名の相談がある、メモがない、結果がない、検索直後に削除された、別会社IDを指定された、予算を超える、停止された、参照文に命令が含まれるケースを含める。検索結果が似ているだけで関係ない決定を持ち込まないかも評価する。

この段階では設計書のみ。実装開始時には既存ブランチのマージ状態を確認し、専用ブランチに分ける。実装後の確認が終わるまでマージしない。
